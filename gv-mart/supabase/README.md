# GV Mart — Supabase schema

Authority order for every value/rule in this schema: `GVMart-Requirement-Confirmation v2.2.pdf` > `GV_Mart_Design_Deltas_for_ClaudeDesign.md` > `GV_Mart_Vite_Implementation_Plan.md` > `GV_Mart_ClaudeCode_BuildSpec.md` §5 (base data model).

## Layout

- `migrations/` — SQL migrations, applied in filename order. One domain per file: enums → tables (10 files, grouped as in BuildSpec §5) → helper functions/triggers → RLS policies.
- `seed/data.ts` — pure seed data (org, 5 role logins, catalog, suppliers, 25 Chennai customers). No Supabase calls — importable by tests.
- `seed/seed.ts` — runs the actual inserts via `@supabase/supabase-js` using the `service_role` key. Entry point: `npm run seed`.
- `functions/` — reserved for Edge Functions (payroll, approvals, auto-PO, WhatsApp, AMC billing) — added from Phase 5 onward per the Vite plan.

## First-time setup against a real Supabase project

```bash
npx supabase login
npx supabase link --project-ref <your-project-ref>
npx supabase db push              # applies migrations/*.sql in order
```

Then in `.env.local` (browser-safe vars only):

```
VITE_SUPABASE_URL=https://<project-ref>.supabase.co
VITE_SUPABASE_ANON_KEY=<anon key>
```

And in your shell (service_role — never in `.env.local`, never committed):

```bash
export SUPABASE_URL=https://<project-ref>.supabase.co
export SUPABASE_SERVICE_ROLE_KEY=<service_role key>
npm run seed
```

## Local dev with the Supabase CLI (Docker)

```bash
npx supabase start                # spins up local Postgres/Auth/Studio via Docker
npx supabase db push --local
SUPABASE_URL=http://127.0.0.1:54321 SUPABASE_SERVICE_ROLE_KEY=<from `supabase status`> npm run seed
```

## Regenerating `src/types/database.ts`

Against a real/local project:

```bash
npx supabase gen types typescript --local > src/types/database.ts   # or --project-id <ref>
```

(This repo's current `database.ts` was generated by introspecting the applied schema directly, since neither Docker nor a live project was available in the scaffolding environment — same output shape, just a different generation path. Regenerate it the normal way once you have a real project linked.)

## Design notes / deviations from the BuildSpec draft

- `settings` is one typed row per org (not a generic key/value table), and the redundant `organizations.settings jsonb` column from the BuildSpec draft was dropped — `settings` is the single source of truth for per_km_minutes, geofence radius, work hours, discount caps, etc.
- `technicians.zone` was dropped — the v2.2 Design Deltas explicitly list "Zone/Area Master" under "DO NOT ADD," and it's ENHANCE-only (not APPEARS) on ADM-14.
- `invoices.payment_description` was added — v2.2 §6.1 requires a short description alongside the transaction ID for bank transfers; the BuildSpec draft's column list was missing it. Enforced with a CHECK constraint.
- No `DELETE` RLS policies exist yet anywhere — hard deletes aren't part of any UI yet, so the safe default (RLS denies) applies everywhere. Add per-module delete policies when a delete flow actually ships.
- `incentive_rules` and `salaries` are seeded with **zero rows** — v2.2 explicitly forbids hardcoded incentive/salary figures; those are admin-configured via the Masters UI (Phase 4 / Stage 4).
